# 08 · 关键决策记录

> 只记"为什么是这样"。每一条都对应代码里真实存在的实现，不是设想。

## 一、存储

| # | 决策 | 理由 | 放弃的方案 |
|---|---|---|---|
| 1 | **单文件加密容器**（`ontology.po.json`） | 搬家只需复制一个文件；没有数据库依赖；用户能亲手备份 | 本地 SQLite（口令保护弱、迁移易漏 -wal/-shm） |
| 2 | **PBKDF2 200 万次 + AES-256-GCM** | 只用标准库与 `cryptography`；iOS 侧可对等实现 | Argon2（依赖重、跨端难）、纯口令哈希（无法加密） |
| 3 | **原子替换写盘** | 断电不会得到半截容器 | 直接覆写 |
| 4 | **分三段**（ontology / model_service / ledger） | 写流水不重写本体（已断言密文逐字节不变） | 单段（大库写入会越来越慢） |
| 5 | **不做明文缓存** | 宁可慢一点，也不落明文 | 明文缓存加速（一旦落盘就违背承诺） |

## 二、数据模型

| # | 决策 | 理由 |
|---|---|---|
| 6 | **RDF + SHACL 作为数据层** | 属性可扩展、校验声明式、可导出标准格式 |
| 7 | **新集合用专属谓词** | 规避 `rdfs:domain` 推理把节点重新定型（见 02 坑 1） |
| 8 | **每次写入全量校验** | 宁可慢，不容忍坏数据；批量场景用 `put_many` 摊薄 |
| 9 | **删除保护（被引用即拒绝）** | 防止悬空引用；级联由调用方显式做 |
| 10 | **资料拆成 `profile-items`** | 只有拆开才能"只授权其中一项" |

## 三、授权模型

| # | 决策 | 理由 | 放弃 |
|---|---|---|---|
| 11 | **给"圈"授权，不一个个点** | 关系是天然的授权单位 | 只支持个体授权 |
| 12 | **一个主体可在多个圈** | 现实如此（家人+工作+同学） | 单一归属 |
| 13 | **圈不嵌套** | 推理简单、可解释；嵌套会让"谁能看"变得难以说清 | 树形组织 |
| 14 | **圈里只存关系** | 别人的证件/住址不该进我的库 | 存对方全档 |
| 15 | **代理 `acts_for`** | 智能体替人办事是常态，不继承就没法用 | 每个智能体单独授权 |
| 16 | **代理只能指向人/角色** | 防止代理链套娃与越权 | 智能体代理智能体 |
| 17 | **判定必须带 `matched_via`** | 只给结论的授权系统无法被信任 | 只返回 allow/deny |
| 18 | **证件类默认 `critical`** | 泄露代价最高；查看必须二次确认 + 留痕 | 与其他字段同等对待 |

## 四、个人数据

| # | 决策 | 理由 |
|---|---|---|
| 19 | **通讯录备注也导入** | 备注是唯一能承载自定义分类的字段（你选了"带备注"） |
| 20 | **但一律 `restricted`** | 备注常含第三方隐私：不授权、不进契约、导出排除、可逐条删 |
| 21 | **资产只存掩码与摘要** | 完整卡号没有任何必要入库 |
| 22 | **流水存明细、放独立段** | 需要核对账目，但绝不能拖慢本体（你选了"存流水"） |
| 23 | **通讯录按稳定 ID 就地更新** | 改名/改电话不能产生重复，这是用户最担心的问题 |
| 24 | **手机删掉的人只标记不删除** | 手机可能是"部分同步"，直接删会误删真实联系人 |
| 25 | **设备用完整序列号区分** | 同型号两台手机不能混；后四位不够 |

## 五、界面

| # | 决策 | 理由 |
|---|---|---|
| 26 | **两层导航 22 项** | 日常（我的世界）与专业（规则与能力）分开；不需要再切模式 |
| 27 | **不用原生 confirm/alert** | 原生弹窗不可定制、文案无法解释后果 |
| 28 | **不用 prompt** | 同上；一律用 `#record-dialog` |
| 29 | **空状态必须给下一步动作** | 空白页面等于死路 |
| 30 | **占位页不放假数据** | 宁可显示"还没做"，也不演示假象 |
| 31 | **每次查看明文都留痕** | 查看即泄露点；界面文案不得承诺未实现的事（曾有不实文案，已修） |
| 32 | **卡片内控件 12px/28px** | 默认表单尺寸会撑破卡片（真实返工） |

## 六、工程

| # | 决策 | 理由 |
|---|---|---|
| 33 | **无构建步骤的前端** | 单机工具，改完刷新即可；不需要 Node 工具链 |
| 34 | **测试是可执行脚本而非 pytest** | 零依赖、单文件可跑、输出即报告 |
| 35 | **部署 = 复制 + 重启** | 没有容器与编排，运维成本最低 |
| 36 | **先编译后写盘** | 曾把坏代码写进仓库（靠回滚救回） |
| 37 | **每次部署前跑闸门** | 闸门救过多次（例：删圈被变更记录挡住，上线前拦下） |

## 七、明确不做（以及为什么）

```
✗ 云同步         与"数据只在自己手里"冲突；用户要备份就复制文件
✗ 多用户         个人工具；多用户会把"谁的库"这件事搞复杂
✗ 明文缓存       违背承诺
✗ 抓取微信数据   违反平台规则、不稳定、且不属于"第一性数据"
✗ 手机端（一期） 先把手上的八块做扎实（决定：后面再做）
✗ 在浏览器里读 USB 设备   浏览器没有这个能力；只能由本机后端调 adb
```
