# 在个人本体软件上使用「专业技能」的人，至少需要具备哪些能力

> 适用对象：想把自己的专业判断装进本软件、并以「场景切片」形式对外交付的人。
> 结论先说：**不需要会编程、不需要会 JSON、不需要懂本体论。** 需要的全部是**你自己专业里的判断力**，
> 外加**把它拆成结构化条目的耐心**。

---

## 一、总览：能力分三档

| 档位 | 内容 | 说明 |
|---|---|---|
| **必备**（缺一件就做不完） | 一~五 | 专业判断的表达能力 + 结构化拆解 + 给数字 + 必填意识 + 软件操作 |
| **加分**（有则质量更高） | 六~七 | 验证习惯 + 迭代意识 |
| **不需要** | 八 | 编程 / JSON / 本体论 / 数据库 |

---

## 二、必备能力

### 1. 能说清自己的专业判断（表达能力）

要能用**大白话**讲清这四件事，因为软件的第一步就是你说、它转成草稿：

- 我**看哪几件事**（观察点/信号）；
- 每件事**什么情况算异常**（阈值、比较方式）；
- **几件事同时出现**时，结论要升级还是维持；
- **什么情况是例外**（我的规则要打折或改写）。

> 练法：对着手机录音讲 3 分钟自己的判断流程，回放听 —— 讲不清的地方，就是软件里会卡住的地方。

### 2. 能把判断拆成软件的结构（结构化拆解）

不用记界面名称，但要能**把判断分到下面这些"格子"里**（软件里的八个部分）：

| 格子 | 你要回答的问题 | 对应界面 |
|---|---|---|
| 我要知道的信息 | 做这个判断**必须先知道**哪些值？ | 字段清单（**全部必填**） |
| 不同行业的侧重 | 不同情形下，各维度的**重要性比例**是多少？ | 权重表 |
| 判断的基准线 | 基准值是多少？什么条件下降/上调？ | 阈值与调整 |
| 我观察什么 | 每个观察点**怎么判定**（字段+比较+值），**属于哪个维度** | 信号清单 |
| 几个观察点一起出现时 | 哪些观察点同时成立 → 什么结论、多严重 | 组合规则 |
| 例外情况 | 哪种情况下规则要改写/降权 | 例外规则 |
| 我的依据 | 每条结论**引哪条依据**（法条、规范、内部标准） | 依据清单 |
| 打分线 | 分数到多少 → 什么结论 | 分数段 |
| （兜底） | 什么都不成立时，默认结论是什么 | 兜底结论 |

**核心要求：会用「维度」给观察点归类。** 软件算分的方式是
`分数 = 命中的观察点各自维度的权重之和` ——
所以**每个观察点都要挂一个维度**（软件里写作 `观察点 ｜ 维度名`），否则权重算不起来。

### 3. 能给数字（量化能力）

- 阈值：`基准值 1.0`、`上调 0.2` 这类**你自己的数字**；
- 权重：各维度/各行情的相对比例（如 0.2 / 0.2 / 0.25 / 0.35，**和为 1 更好读**）；
- 分数段：`≥0.5 → 结论A`。

**软件不会替你提供任何数字。** 它只做算术。**数字来自你的专业经验**，这也是这份资产的价值所在。

### 4. 知道"什么是必要前提"（必填意识 —— 最容易吃亏的一条）

软件的约定是：**「我要知道的信息」里列的字段，全部必填**；
**少任何一项，判定不会给结论，只返回「信息不足，无法判断」，并告诉你缺哪几项。**

所以你要能判断：**哪些信息是"没有它我就不该下结论"的**。
- 列多了 → 调用方经常缺项，体验差；
- 列少了 → 信息不全也出结论，专业上不安全。
> 建议：宁可**少而硬**，不要"看着全面"。先确保"缺了它我绝不表态"的那几个字段。

### 5. 会用软件完成七步（操作能力，门槛很低）

| 步 | 你要做的事 | 会不会难 |
|---|---|---|
| 1 | 建**主体**：一个「本人」（授权方），一个你要交付的对象 | 会打字即可 |
| 2 | 建**场景切片**：把场景说清楚，选一种方式生成框架（模型起草 / 一行一条自己写） | 会打字即可 |
| 3 | 在**核对与微调**里逐项改：权重、阈值、观察点、组合、例外、依据、分数段 | 会填表即可 |
| 4 | **保存**（保存＝草稿，不影响对外） | 点按钮 |
| 5 | **确认并启用** → 选**授权方**与**被授权方**（被授权方要从"已批准的本机程序"里选） | 点两次 |
| 6 | 让调用方先连一次 → 在**本机程序**页**批准**它并勾上 `judgment` 范围 | 点按钮 |
| 7 | **场景预演**：故意少填一项 → 应看到「信息不足」+ 缺项标红；填全 → 应看到结论 | 试两次就会 |

> **明确不需要：** 会编程 ✗、会写 JSON ✗、会命令行 ✗、懂数据库/本体论 ✗。
> 「一行一条」的写法就是为"不会技术的人"设计的：一行一个观察点，末尾用 `｜ 维度名` 标维度。

## 三、加分能力

### 6. 验证习惯（把"我觉得对"变成"我试过对"）

- **必填测试**：故意缺一项，确认它**不给结论**（而不是硬给一个）；
- **边界测试**：金额超上限、用途不在允许范围 → 应**拒绝给结论**；
- **反向测试**：把明显该出 A 结论的数据喂进去，看是否出 A；
- **依据测试**：确认结论后面确实跟着你的依据，且**只在相关观察点都命中时才引**。

### 7. 迭代意识（把它当资产维护，不是一次性配置）

- 每次调整都能说清"为什么调"（软件里有**调整记录**，建议逐条写）；
- 收集被拒绝/被判"信息不足"的案例，反过来修字段与阈值；
- 关注**置信度**：目前软件只标注"未验证"，**置信度演进尚未实现**（见第四节），
  所以现阶段"置信度"靠你自己的记录来维护。

## 四、当前软件**还不能**替你做的事（如实告知，别把期望放太高）

| 事项 | 现状 |
|---|---|
| 计费 | 尚未实现（可先做演示性质） |
| 审计留痕 | **已实现**：每次对外判定写一条判定记录，含结论/依据/调用方/时间 |
| 置信度自动演进 | **未实现**（框架里有"调整记录"可人工维护） |
| 作者签名/防伪 | 未实现（`owner_signature` 目前只是占位） |
| 调用方身份 | **已实现**：由系统内核识别调用方进程（不靠可被复制的令牌），你批准后它才能调 |
| 框架保密 | 尚有缺口：调用方目前仍可能读到框架与权重（**待修**，已记在开发待办里） |

## 五、自检清单（十问，能全答"是"就可以开始）

1. 我能否用大白话讲清我的判断流程（3 分钟讲完）？
2. 我能否列出"缺了它我绝不表态"的必填字段？
3. 我能否给每个观察点挂上一个维度？
4. 我能否给出维度之间的相对权重（不用精确，比例合理即可）？
5. 我能否说出每个观察点的判定条件（字段 + 比较 + 值）？
6. 我能否举出"几个观察点同时成立 → 结论升级"的例子？
7. 我能否举出至少一条"例外情况"？
8. 我的结论能否对应到可引用的依据？
9. 我能否给出"分数 → 结论"的分档？
10. 我是否愿意用预演页试错两次，而不是直接对外？

> **十条里缺一两条也能开始**：软件支持先存草稿、再逐步补。
> 缺第 2、3、9 条的人**最容易在最后一步卡住**（算不出分 / 不给结论 / 不知道结论从哪来）。

---

## 六、一句话总结

> 用这个软件不需要技术能力，需要的是**你对自己专业判断的清晰度**：
> **看得见观察点、给得出数字、说得出前提、认得下例外、引得起依据。**
