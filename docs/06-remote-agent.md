# 跨机使用：让另一台机器上的智能体访问本机本体

状态：已实现（方案 A：SSH 隧道 + 远端运行 MCP 服务）
适用范围：智能体运行在**另一台机器**、本体数据留在本机 Mac 的场景

## 1. 为什么需要专门处理

当前架构里，**MCP 使用 stdio 传输**：智能体客户端把 `python -m backend.mcp_server` 作为
**自己的子进程**启动，双方通过 stdin/stdout 收发 JSON-RPC。这带来一条硬限制：

> 远程机器上的客户端**无法启动**你 Mac 上的进程。所以 stdio MCP 天生只能同机使用。

而本机运行的两个 HTTP 服务都只监听 `127.0.0.1`，局域网里也访问不到——这是**有意的**：

- 接口的唯一凭据是本机会话令牌，**没有 TLS、没有按智能体分发的可撤销凭据、没有针对远程来源的防护**；
- 而 `/v1/*` 能**读取整个本体**（主体、场景、偏好、规则、判定记录）。

因此**不要**为了让远程访问而把 `PERSONAL_ONTOLOGY_HOST` 改成 `0.0.0.0`：那等于把本体
暴露给同网段任何人。管理器里的 Origin 白名单只用于挡浏览器 CSRF，**不挡 `curl` 与脚本**。

本方案的做法是：**本机不新增任何网络暴露**，远程通过 SSH 隧道访问，MCP 服务跑在远端。

## 2. 拓扑

```
        ┌──────────── 远端机器（智能体所在）─────────────┐
        │  WorkBuddy / Muse Code                         │
        │      │ stdio（本机子进程）                      │
        │      ▼                                          │
        │  scripts/mcp-remote.sh ──► backend.mcp_server   │
        │                                │ HTTP           │
        │                                ▼                │
        │                        127.0.0.1:8765（隧道入口）│
        └────────────────────────────────┼────────────────┘
                                         │ SSH 加密隧道
        ┌────────────────────────────────┼────────────────┐
        │  Mac（本体所在）                ▼                │
        │  管理器 8765 ──代理 /v1/*──► 治理后端 8766       │
        │  两者都只监听 127.0.0.1                          │
        └──────────────────────────────────────────────────┘
```

远程只转发 **8765**（管理器）。后端 8766 不需要、也不应该暴露。

## 3. 步骤

### 3.1 Mac 侧（一次性）

1. 开启 SSH：系统设置 → 通用 → 共享 → **远程登录**。
   建议只允许密钥登录，并把隧道限制在本机回环上（`-L` 默认就是）。
2. 确认服务在跑：`~/personal-ontology/start.sh`
3. 用控制台解锁本体（**每次解锁都会生成新令牌**）：打开 http://127.0.0.1:8765 输入登录密码。

### 3.2 远端机器（一次性）

MCP 服务只依赖标准库，**不需要 pip 安装任何东西**，但需要 **Python 3.11 或更新**
（用到 3.10+ 的类型语法）。复制三个文件即可：

```bash
mkdir -p ~/personal-ontology-mcp/backend
scp <你的Mac>:~/personal-ontology/backend/{__init__.py,config.py,mcp_server.py} \
    ~/personal-ontology-mcp/backend/
scp <你的Mac>:~/personal-ontology/scripts/mcp-remote.sh ~/personal-ontology-mcp/
chmod +x ~/personal-ontology-mcp/mcp-remote.sh
```

### 3.3 建立隧道（保持运行）

```bash
ssh -N -L 8765:127.0.0.1:8765 <你的Mac>
```

这条命令把**远端的** `127.0.0.1:8765` 通过 SSH 加密隧道接到 Mac 的管理器。
`-N` 表示只转发、不开 shell。隧道断掉后远程智能体即不可用（会收到明确错误）。

### 3.4 配置智能体客户端

把 MCP 配置的 `command` 指向包装脚本（**不要直接指向 python**，那样拿不到令牌）：

```json
{
  "mcpServers": {
    "personal-ontology": {
      "command": "/Users/<你>/personal-ontology-mcp/mcp-remote.sh",
      "env": { "PO_REMOTE": "user@example-host.local" }
    }
  }
}
```

包装脚本会：① 检查 Python 版本；② 检查隧道是否就绪；③ 通过 SSH 取回解锁期令牌；
④ 以 stdio 启动 MCP 服务。

可用环境变量：`PO_REMOTE`（必填）、`PO_REMOTE_HOME`（默认 `personal-ontology`）、
`PO_LOCAL_PORT`（默认 `8765`）、`PO_MCP_HOME`（默认 `~/personal-ontology-mcp`）、
`PO_PYTHON`（默认 `python3`，需 3.11+）、`PO_SSH_OPTS`。

## 4. 行为与限制

| 情况 | 表现 |
|---|---|
| 本体已锁定 | 包装脚本明确提示"请在那台 Mac 的控制台解锁后重试"，不启动 MCP |
| 隧道未建立 | 提示需要先运行的 `ssh -N -L ...` 命令 |
| Python 版本过低 | 提示需要 3.11+，并可用 `PO_PYTHON` 指定 |
| **本体重新解锁过** | 旧令牌失效，工具返回"会话令牌已失效……需要重启本 MCP 连接"——**重启客户端即可** |
| 空闲锁定到期 | 同上；需要重新解锁并重启 MCP 连接 |

**这不是"无人值守"方案**：密钥由登录口令派生、只在解锁期间驻留内存。
远程智能体可用，前提是你在 Mac 上解锁着本体。若希望长时间无人值守使用，
需要另行设计（例如把凭据放进系统钥匙串），那会改变威胁模型，见 `05` 的取舍。

## 5. 安全要点

- Mac 侧**不要**改 `PERSONAL_ONTOLOGY_HOST`；保持 `127.0.0.1`。
- 隧道**只转发 8765**，不要转发 8766。
- SSH 用密钥登录并设口令保护；关闭密码登录。
- `data/session-token` 是**本机**凭据文件（0600），只在解锁期间存在；远端靠 SSH 取回，
  **不要**把它复制到远端长期保存——它随每次解锁变化，且等价于访问凭据。
- 远端机器本身的安全等级应不低于 Mac：它持有可读取本体的会话令牌（内存中）。
