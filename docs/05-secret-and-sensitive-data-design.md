# 本体加密、登录与解锁设计（v2.1，评审稿）

状态：设计稿，待评审。
本稿取代 v2（KDF 选型未定、登录仍用 api-token 文件）与 v1（字段级加密 + 同盘密钥，骨架作废）。

**已定决策**：KDF 用 PBKDF2（iOS 零依赖）；LLM 凭据纳入容器保护；**登录改为密码方式**，取代 `data/api-token`。

---

## 0. 为什么换骨架

v1 只加密 `ContactPoint.value`，密钥以明文文件与数据同目录。对目标威胁三条全部失效：本体数据 100% 是明文 Turtle；密钥同账户可读；99% 的数据没进加密范围。

v2.1 的三条硬性前提：

1. **整图加密**：本体文件整体是密文，连 ID、关系、时间戳、场景原文都不泄露。
2. **密钥来自口令，不以可用形式落盘**：文件与口令的信任域分离。
3. **盘上零明文、且零长期凭证**：没有明文数据，也没有可被读走的长期令牌（见 §5）。

## 1. 威胁模型

**覆盖**（对手最终都拿到"文件"）：

| # | 对手 | 说明 |
|---|---|---|
| T1 | 设备上的恶意程序 | 直接读取本体文件。Mac 先行，后续有 iPhone/iPad 客户端 |
| T2 | 拿到机器或磁盘的人 | 物理接触、拆盘、整机丢失 |
| T3 | 拿到本体文件的人 | 文件被拷走、同步到别处、被误传 |

**不覆盖**：已完全控制登录会话且能在解锁期间读取进程内存（需调试权限或 root）；解锁期间的屏幕/剪贴板/键盘窃取；口令被钓鱼；历史明文在未覆盖块中的残留（见 §8.3）。

## 2. 架构总览

```text
   控制台 / iOS App
        │  ① 首次：设置登录密码   ② 之后：输入密码登录（=解锁）
        ▼
   ┌──────────────────────────────────────────────┐
   │ 后端服务（Mac）                                │
   │  未初始化：无容器 → 引导设置密码（409）          │
   │  已锁定  ：内存无密钥无图 → 要求登录（401）      │
   │  已解锁  ：容器解密到内存 → 内存会话令牌          │
   │  写入    ：图 → Turtle → AES-256-GCM → 原子替换  │
   └───────────────────────┬──────────────────────┘
                           │
              ontology.po.json（永远是密文）
                           │
              可安全同步 / 备份 / 拷走
```

**登录即解锁**：密码同时用于身份认证与派生容器密钥，不再有独立的令牌文件。

## 3. 容器格式规格（可移植，iOS 必须能实现）

单个 JSON 文档：任何平台都能解析，避免二进制字节序问题。约 35KB 本体加密后约 47KB。

### 3.1 结构：一个文件，两个独立加密段

**格式已冻结**：`version: 1` 是跨实现契约，字段名、AAD 拼接与算法参数不得再变；变更须升版本号。

```json
{
  "format": "personal-ontology-container",
  "version": 1,
  "revision": 42,
  "created_at": "2026-10-01T12:00:00Z",
  "updated_at": "2026-10-01T20:15:00Z",
  "sections": {
    "ontology": {
      "kdf": { "name": "pbkdf2-hmac-sha256", "salt": "<base64,16B>", "iterations": 2000000, "dklen": 32 },
      "cipher": { "name": "AES-256-GCM", "nonce": "<base64,12B>" },
      "ciphertext": "<base64, 密文 || 16B tag>"
    },
    "model_service": {
      "kdf": { "name": "pbkdf2-hmac-sha256", "salt": "<base64,16B>", "iterations": 2000000, "dklen": 32 },
      "cipher": { "name": "AES-256-GCM", "nonce": "<base64,12B>" },
      "ciphertext": "<base64, 密文 || 16B tag>"
    }
  }
}
```

**为什么是两个段而不是两个文件**：改口令需要同时重写本体与模型凭据。两个文件的重命名**不是一对原子操作**——写成功一个、失败另一个，就会变成"本体用新口令、凭据用旧口令"，用户看到的是莫名其妙的"配置无法读取"。单文件写临时文件 + 一次 `os.replace` 是原子的，要么全成要么全不成（详见 §4.5）。

**为什么两个段各有自己的 salt**：密钥分离。两把密钥从同一口令派生但互不可推导，一段泄露不波及另一段。

**未改动的段原样搬运**：写文件时若 `model_service` 段没有变化，直接沿用其原有字节（同 salt、同 nonce、同密文），**不需要把 API Key 解密进内存**。这让日常本体写入既不触碰凭据，也避免 nonce 复用。

**模型服务段按需解密**：解锁时只解密 `ontology` 段；`model_service` 段在真正需要调用模型时才解密。

### 3.2 算法（固定，不提供选择）

| 用途 | 算法 | 参数 |
|---|---|---|
| 口令派生 | **PBKDF2-HMAC-SHA256**（RFC 8018 / NIST SP 800-132） | salt 16B 随机；**iterations 2,000,000**；输出 32B |
| 加密 | **AES-256-GCM** | 256 位密钥；96 位随机 nonce；128 位 tag |
| 明文载荷 | 现有 Turtle 序列化（UTF-8） | 保持 rdflib / SHACL 逻辑不变 |

**迭代次数的实测依据**（本机 Apple Silicon，PBKDF2-HMAC-SHA256）：

| 迭代次数 | 耗时 |
|---|---|
| 100,000 | 12 ms |
| 600,000（OWASP 建议下限） | 71 ms |
| **2,000,000（本设计取值）** | **约 236 ms** |

iOS 的 CommonCrypto 通常慢 2–4 倍，即约 **0.5–1 秒**——对一次性解锁可以接受。迭代次数写在容器头部，**将来可以提高而不破坏旧文件**（旧文件按自身头部参数解密）。

**AAD（附加认证数据）**：绑定头部参数，防止头部被篡改。精确构造以便跨语言复现（不做"规范化 JSON"）：

```
aad = "po-container-v1|" + section + "|" + version + "|" + salt_b64 + "|" + iterations + "|" + nonce_b64
```

ASCII 拼接，整数十进制无前导零。解密方必须用同样方式重建，否则 `InvalidTag`。

### 3.3 跨平台实现路径：两边都零第三方依赖

| 组件 | Python（Mac 后端） | Swift（iOS/iPadOS） |
|---|---|---|
| AES-256-GCM | `cryptography` 的 `AESGCM`（现有依赖） | **CryptoKit `AES.GCM`（系统内置）** |
| PBKDF2-HMAC-SHA256 | **`hashlib.pbkdf2_hmac`（标准库）** | **CommonCrypto `CCKeyDerivationPBKDF`（系统内置）** |

这正是选 PBKDF2 的理由：iOS 侧无需引入任何库。代价是 PBKDF2 抗 GPU/ASIC 爆破能力弱于 scrypt/Argon2id，因此**口令强度要求相应提高**（§4.3），且迭代次数取到可接受的较高值。

### 3.4 测试向量

规格必须附固定测试向量（口令、salt、iterations、nonce、期望密文与 AAD），Swift 与 Python 用同一组互验。**没有测试向量的格式规格不算冻结。**

### 3.5 测试向量（已冻结）

任何语言的实现都必须用下列固定输入产出**完全相同**的密文，否则视为不兼容。向量用小迭代次数以便快速核验；生产路径必须使用随机 salt 与随机 nonce。

| 输入 | 值 |
|---|---|
| section | `ontology` |
| version | `1` |
| password | `correct horse battery staple` |
| salt | 十六进制 `000102030405060708090a0b0c0d0e0f`（base64 `AAECAwQFBgcICQoLDA0ODw==`） |
| iterations | `1000` |
| nonce | 十六进制 `101112131415161718191a1b`（base64 `EBESExQVFhcYGRob`） |
| 明文 | `测试向量：personal-ontology container v1`（UTF-8；base64 `5rWL6K+V5ZCR6YeP77yacGVyc29uYWwtb250b2xvZ3kgY29udGFpbmVyIHYx`） |

## 4. 登录、解锁与锁定态

### 4.1 三个状态

| 状态 | 条件 | 行为 |
|---|---|---|
| **未初始化** | 无容器文件 | 除 `/health` 外一律 **409** `{"error":"ontology_uninitialized"}`，前端引导设置密码 |
| **已锁定** | 有容器、无有效会话 | 除 `/health`、`/v1/login` 外一律 **401** `{"error":"login_required","message":"本体已锁定，请输入登录密码。"}` |
| **已解锁** | 有有效会话 | 正常 |

未登录与已锁定是同一个状态，因此统一用 401（不像 v2 那样区分 423），前端只需呈现一个密码输入界面。

### 4.2 端点

| 端点 | 说明 |
|---|---|
| `GET /health` | 无需认证；返回 `{"locked":bool,"initialized":bool}` |
| `POST /v1/setup {password}` | 仅未初始化时可用；设置密码并创建（或迁移，见 §8）容器；成功后直接进入已登录 |
| `POST /v1/login {password}` | 用容器头部参数派生密钥 → 解密 → 成功即解锁；返回内存会话令牌 |
| `POST /v1/logout` | 结束当前会话 |
| `POST /v1/lock` | 丢弃内存中的密钥与图，并使**所有**会话失效 |
| `PUT /v1/account/password {current,new}` | 修改登录密码（= 重新加密容器），见 §4.5 |
| 其余 `/v1/*` | 需带会话令牌；未登录返回 401 |

**登录失败防护**：连续失败按指数退避（1s/2s/4s…上限 30s）；失败日志只记"第 N 次失败"，不记口令与长度。注意：**攻击者拿到文件后可离线爆破**，因此退避只是补充，真正的防线是口令强度与迭代次数。

### 4.3 口令策略（下限 8 字符 + 三条补偿规则）

**已定：最少 8 个字符。** 但纯长度不是有效的防线——PBKDF2 抗 GPU 爆破弱，同样 8 个字符在不同构成下相差 8 个数量级。离线爆破成本实测估算（PBKDF2 @ 2,000,000 次，本机 236 ms/次）：

| 口令类型 | 单台 GPU | 8 卡 GPU 集群 |
|---|---|---|
| 8 位**常见口令**（字典 10 万条） | 1.7 分 | **12.5 秒** |
| 8 位纯小写随机 | 6.6 年 | 10 个月 |
| 8 位大小写 + 数字随机 | 6.9 千年 | 865 年 |
| 5 个 diceware 词 | 900 百万年 | 112 百万年 |

因此接受 8 字符下限的同时，**必须**配合：

1. **拒绝常见口令**：内置高频口令表（`password1`、`12345678`、`qwerty`、日期、重复字符、键盘序列等）与规律检测，命中即拒绝。这一条直接消除表中"12.5 秒"那一行，是三项里最有效的。
2. **要求字符类别 ≥ 3**：小写 / 大写 / 数字 / 符号中至少三类，把攻击空间从 `26^8` 抬到 `62^8` 以上。
3. **强度提示不阻断但显著告警**：低于约 50 bit 熵时显示明确警告（"此类口令可能被离线爆破"），并要求勾选知悉；界面同时**推荐**（不强制）5 个 diceware 词。

明确告知"忘记密码 = 数据不可恢复"，并要求勾选知悉。

**可选加固（建议）**：把迭代次数从 2,000,000 提到 3,000,000——本机约 354 ms、iOS 约 0.7–1.5 秒，攻击成本线性增加 50%。迭代次数写在容器头部，提高不影响旧文件读取。

### 4.4 会话

- 登录成功后，后端生成随机会话令牌，**只存在后端内存**（含过期时间）；浏览器存 `sessionStorage`。
- 后端重启 → 所有会话失效 → 需重新登录（同时即重新解锁）。
- 空闲自动锁定 **默认 30 分钟**（滑动过期：每次请求续期）；触发时丢弃密钥与图并结束所有会话。
  时长可配置：`data/settings.json` 的 `session_timeout_minutes`（0 = 不自动锁定），
  由 `PUT /v1/account/session-timeout` 修改，「登录与安全」页提供选项。

### 4.5 修改登录密码（取代"密钥轮换"）

口令只有一个，因此改密码会**同时重新加密容器中的两个段**（`ontology` 与 `model_service`，见 §6）。

**事务流程（力求"要么全成、要么全不成"）**：

```text
1. 校验当前密码：用它解密 ontology 段（失败即拒绝）
2. 全局写锁：暂停其他写入（避免改密期间并发写丢数据）
3. 用新密码 + 各段新 salt 派生两把新密钥，重新加密两个段
4. 在同目录写临时文件 → fsync → 一次 os.replace 覆盖容器
       （单文件单次替换 = 原子：崩溃时旧文件完好，旧密码仍可用）
5. 释放写锁；丢弃内存中的旧密钥，用新密钥替换
6. 使所有会话失效、删除解锁期临时凭证（§5）→ 要求重新登录
```

**失败模式分析**：

| 情形 | 结果 |
|---|---|
| 第 3 步失败（内存不足等） | 未写盘，容器保持原样，旧密码照常可用 |
| 第 4 步中途崩溃/断电 | 临时文件残留，正式容器未被替换 → 旧密码照常可用；下次启动清理临时文件 |
| 第 4 步成功、第 6 步前崩溃 | 容器已是新密码；重启后需用新密码登录（旧密码失效，属预期） |
| 并发写入 | 被第 2 步的写锁挡住，不会丢数据 |

**对正常数据操作的影响：无。** 数据本身不变，只是换了密钥重新加密；改密结束后 store 继续用新密钥读写，其余逻辑一律不变。

**两处用户可见的变化**（必须在界面说明）：

1. **所有会话失效**，包括其他设备与 MCP 子进程 —— 需要重新登录；
2. **历史加密备份仍由旧密码保护**。改密码不会（也无法）改变已导出的备份——它们仍要用旧密码打开。界面提供"用新密码重新导出备份"的提示入口。

## 5. 凭据模型：盘上不存在长期凭证

现状 `data/api-token` 是**长期有效且同账户任意进程可读**的文件——这与威胁模型直接冲突。改为：

| 凭据 | 存放 | 生命周期 |
|---|---|---|
| 登录密码 / 容器密钥 | **不落盘**。密码只在 `POST /v1/login` 请求体中出现一次 | 一次请求 |
| 派生密钥 | 仅内存；锁定/退出时尽力清零 | 解锁期间 |
| 会话令牌 | 后端内存 | 直到登出、锁定或重启 |
| 密码验证器 | **不单独存储**——容器自身的 GCM tag 就是验证器 | — |
| 解锁期临时凭证（供 MCP 子进程） | `data/session-token`，0600 | **仅在解锁期间存在**，锁定或退出时删除 |

**MCP 子进程的认证**：本机 MCP 由客户端拉起，无法交互式输入密码。做法是——解锁期间后端把当前会话令牌写入 `data/session-token`（0600），MCP **每次调用前重新读取**（现有实现是启动时读一次，需改为按调用读取）；锁定后文件不存在，MCP 得到明确文案"本体已锁定，请让用户先在控制台解锁。"

收益：**磁盘上不存在任何长期有效的凭证**。恶意程序在全盘扫描中拿不到可用于访问的令牌。

## 6. LLM 凭据纳入容器（已定）

> **状态：已实现。** 模型配置现位于容器 `model_service` 段（独立盐与 nonce）；升级时旧的 `model-service.json` 与 `model-service.key` 迁入容器后删除。

`model-service.json` 里的 API Key 目前由独立密钥（`model-service.key`）保护且不在容器内。改为：

- 作为**同一容器文件的 `model_service` 段**（§3.1），用**同一密码、独立 salt** 派生第二把密钥加密；
- 该段按需解密：只有真正要调用模型时才解出 API Key，日常本体读写不触碰它；
- 未改动时原样搬运密文，不重复加密、不复用 nonce。

**为什么放在同一文件而不是第二个文件**：改密码要同时重写两者，两个文件的重命名不是原子操作，会出现"一半新口令、一半旧口令"的坏状态（§4.5）。单文件替换消除这个窗口，同时用独立 salt 保留密钥分离。

## 7. 零明文不变量与残留治理

### 7.1 不变量

> 任何时刻，磁盘上都不存在本体明文，也不存在长期有效的访问凭证。

由此得到的简化：

- `_persist()` 的临时文件本身就是密文 → 残留快照不再构成机密性风险；
- 备份 = 复制容器文件 → **天然是加密备份**，"密钥与备份分离"自动成立；
- **字段级加密（`contacts.value` 的 Fernet）不再需要**：容器已整体加密，保留它只会重新引入密钥管理与静默失败。**删除该代码路径与 `contact.key`。**

### 7.2 日志与前端

- 服务日志不含本体内容；错误只写记录 ID 与错误类型。
- 前端不做本地持久化（不写 `localStorage` / IndexedDB）；会话令牌在 `sessionStorage`。

### 7.3 历史明文（如实说明）

SSD/APFS 上无法保证旧数据被物理覆盖：删除后明文仍可能留在 **APFS 本地快照**、Time Machine 备份或未覆写的块中。因此：

- **FileVault 仍然建议开启**——它覆盖的正是这段"历史明文"；
- 迁移步骤包含删除明文文件、残留快照、明文导出，并列出本地快照供用户决定是否删除（`tmutil listlocalsnapshots /`）。

## 8. 从明文迁移到容器

```text
1. 备份现有 ontology.ttl 到用户指定位置（迁移完成后提示删除）
2. 用户设置登录密码（§4.3）
3. 读入明文 Turtle → SHACL 校验 → 序列化 → 加密 → 原子写入 ontology.po.json
4. 重新读取容器并解密 → 与迁移前逐三元组比对
5. 删除 ontology.ttl、残留 ontology-*.ttl、明文导出、以及 data/api-token
6. 报告：容器路径、revision、残留检查结果
```

第 4 步"解密后与原图一致"是验收条件；不一致则保留明文并回滚。

配套改动：`install.sh` **不再生成 `data/api-token`**（该步骤删除），首次密码由用户在控制台设置。

## 9. 跨平台与 iPhone / iPad 路线

- 加密是**文件格式的事**，不是服务的事——手机上不会跑这套 Python 服务。
- **推荐 iOS 原生 App 直接读写容器**（SwiftUI + CryptoKit + CommonCrypto），经「文件」App 或 iCloud Drive 存取；不推荐通过 Mac 上的 API（当前只监听 127.0.0.1）。
- iOS 要点：容器置于沙盒并使用 `NSFileProtectionComplete`；可把密码存入 Keychain（`kSecAttrAccessibleWhenUnlockedThisDeviceOnly`）并用 `LAContext` 做 Face ID 便利解锁——**这只是本机便利，不替代密码**。
- **多设备并发**：容器带 `revision`，写入前比对；磁盘上 revision 更大则拒绝覆盖（"文件已被其他设备更新"）。约定同一时间只有一个写入者，不做自动合并。

## 10. 审计与运行时值的分级（保留项，优先级较低）

容器解决"文件被拿走"，但不解决"解锁期间"与"数据被交给智能体"：

1. **最小化优先于加密**：判定记录 `input_params` 默认只保留约束用到的字段 + 其余字段的 HMAC-SHA256 摘要。
2. **对外显示策略**：`principal_display_mode`（`neutral` 默认 / `full` / `id_only`），控制主体名称是否进入智能体所连模型的上下文。

## 11. 界面设计

### 11.1 首次打开：设置登录密码（取代"粘贴 API Token"）

```text
┌ 设置登录密码 ────────────────────────────────┐
│ 这个密码用于登录控制台，同时加密你的本体数据。   │
│ 密码        [__________________]             │
│ 再输入一次   [__________________]             │
│ 强度        ▓▓▓▓░░  至少 8 位，且含 3 类字符     │
│             （常见口令会被拒绝；推荐 5 个不相关的词）│
│ [ ] 我知道忘记密码后数据无法恢复               │
│                              [创建并加密]     │
└──────────────────────────────────────────────┘
```

若检测到现有明文 `ontology.ttl`，同一界面增加一行"将加密现有本体数据（N 条记录）"。

### 11.2 之后每次打开：登录即解锁

```text
┌ 本体已锁定 ──────────────────────────────────┐
│ 输入登录密码以解锁场景、规则与判定记录。         │
│ 密码 [__________________]      [登录]         │
│ 忘记密码将无法恢复数据。                       │
└──────────────────────────────────────────────┘
```

- 未登录时不渲染、不预取任何本体数据。
- 失败只提示"密码不正确"。

### 11.3 配置与监控 →「登录与安全」

按你的要求，把密码修改放在「配置与监控」下：

| 区块 | 内容 |
|---|---|
| 修改登录密码 | 当前密码 + 新密码（两次）+ 强度提示；执行即重新加密容器并注销所有会话 |
| 锁定 | 「立即锁定」按钮；空闲自动锁定时间设置 |
| 状态 | 容器路径、revision、最后更新时间、KDF 迭代次数 |
| 明文残留检查 | 列出 `ontology.ttl`、残留快照、明文导出、旧 `api-token`，逐项确认删除 |

**不再需要**：密钥指纹、下载密钥副本、钥匙串开关、密钥轮换（改密码即轮换）。
