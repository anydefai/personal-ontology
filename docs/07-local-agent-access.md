# 本机智能体访问控制

状态：已实现（T1+T2+T3+T4）
适用：本体与智能体在**同一台设备**上的场景

## 1. 要解决什么

同机的其他程序不应该在你不知情、未同意的情况下，通过 MCP 读到本体的任何内容。

## 2. 先说清硬限制

以你的用户身份运行的任何程序，都能读你能读的文件、连 `127.0.0.1`、运行你的 Python。
因此**纯软件 + 落盘凭据的方案，原理上无法区分"你批准的智能体"与"以你身份运行的恶意程序"**。
唯一真正的边界是硬件密钥 + 用户在场确认（Touch ID / Secure Enclave），本层未包含。

## 3. 本层做到的四件事

| | 措施 | 效果 |
|---|---|---|
| **T1** | 智能体改走 **Unix 域套接字**（`data/agent.sock`，0600），由内核提供对端 **uid / 可执行文件 / 完整命令行** | **磁盘上不再有可偷的凭据**——没有令牌文件可复制；每个客户端都被具名识别 |
| **T2** | **默认拒绝**：新程序首次连接只登记为"待批准"，控制台「智能体授权」里由你允许或拒绝；授权可列出、可撤销 | **静默读取不可能**；谁在读、读了什么范围一目了然 |
| **T3** | 每个授权带**范围**：`catalog` / `rules` / `decisions` / `principals` / `check` / `preview` / `feedback`，默认不含 `principals` | 限制爆炸半径：为"检查授权"授权的程序拿不到整个本体 |
| **T4** | 后端不可达时的恢复模式**只放行** `health` / `start` / `restart` | 日志、状态、改设置仍需凭据 |

实现要点：网关在**后端进程内**运行，用仅存在于内存的密钥签名身份断言；API 端校验签名，
伪造断言（直接打回环端口）一律无效。管理类接口（授权清单、提权、改设置）**不对智能体开放**。

## 4. 诚实说明：这不是硬边界

同 uid 的恶意程序可以 `exec` 我们的解释器并带同样的参数，从而"长得一样"。本层消除的是
**最廉价、最隐蔽**的那条路（复制令牌文件、静默全量读取），并把**所有新客户端变成可见、需批准**。
要挡住同 uid 恶意程序，需要 T5（Secure Enclave + 用户在场），那是另一轮设计。

## 5. 跨机接入默认关闭

`data/session-token` **默认不再写入**。它一旦存在，同机任何进程都能读它并直接调用 API，
从而绕过智能体授权。确需跨机（SSH 隧道）时在「智能体授权 → 跨机接入」显式开启。

## 6. 自检

`tests/test_agent_access.py` 24/24：未批准一律拒绝、批准后按范围放行、未授予的范围拒绝、
管理接口与自我提权被拒、伪造断言 401、撤销立即生效、再次批准恢复。

## 7. T5（规划中，尚未实现）

用户决定作为后续功能推进。这是唯一能挡住"以你身份运行的恶意程序"的机制——前四层只能
抬高门槛、消灭静默路径，**无法**区分"你批准的智能体"与"同 uid 的恶意代码"。

### 7.1 目标

把"有没有权力读到本体"从**软件判断**变成**硬件 + 用户在场判断**：

- 容器密钥不再单靠口令派生，而由 **Secure Enclave** 中的密钥保护；
- 每次**解锁**都需要 **Touch ID / Apple Watch / 系统密码**确认（`SecAccessControl`
  的 `.userPresence`）；
- **批准新的智能体授权**同样需要用户在场——这样"首次静默访问"在硬件层面也不可能。

### 7.2 设计草图

1. 容器里不放明文 KEK：改为 `container_key` 被一个 **SE 生成的 P-256 公钥**包装
   （ECDH 派生 + AES-GCM 包裹），SE 私钥永不导出、设 `.userPresence`。
2. 解锁流程：用户点「解锁」→ 系统弹出指纹 → SE 完成 ECDH → 解出 `container_key` →
   照现有流程解密容器。口令仍可用于恢复（作为第二条包装路径），否则忘记口令＝数据丢失这条
   约束不变。
3. 授权批准：`POST /v1/agents/{key}/approve` 增加"需要用户在场"的前置校验
   （由本机 helper 调用 LocalAuthentication 完成）。
4. 可选加固：`feedback`（写入）等敏感范围在**每次调用**时要求在场——安全性最高，但 UX 明显变差，
   需先决定是否采用。

### 7.3 取舍与前置决定

| 议题 | 说明 |
|---|---|
| 解锁体验 | 从"输入口令"变成"按指纹 + 系统密码兜底"；macOS 上体验通常更好，但**必须保留口令恢复路径** |
| 迁移 | 现有 `ontology.po.json` 需要重新包装一次（读出口令 → 生成 SE 密钥 → 重写容器） |
| 兼容 | 无 Touch ID / SE 不可用的机器（或非 macOS）回退到当前口令派生方案 |
| 残留风险 | 同一解锁窗口内，同 uid 恶意程序仍可**搭车**（借用已解锁的会话）。要彻底消除必须对每次敏感调用都要求在场——本轮需明确取舍 |
| 实现位置 | Swift / `Security.framework`（`LocalAuthentication` + `SecKeyCreateWithData`）或通过 ctypes 调 Security.framework；对 MCP 与 API 侧只需暴露"一次在场的解锁凭据" |

### 7.4 开工前先定

1. 在场确认的粒度：**每次解锁**（推荐）／每次解锁 + 每次授权批准／每次敏感调用。
2. 是否保留"口令单独可解"作为恢复路径（建议保留，并明确它在威胁模型中的位置）。
3. iOS/iPad 客户端是否同期推进（SE 在移动端同样是唯一硬边界）。
