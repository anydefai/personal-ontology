# 敏感个人信息（实名 / 身份证 / 手机号）该放在哪里：设计草案 v0.1

> 结论先说：**单独一层「个人资料库」，场景只引用、不复制；每次使用都要"限用途 + 限接收方 + 短有效期"，并且全程留痕。**
> 绝不放：场景实例里、调用方那侧、明文文件里。

## 一、为什么不能放进场景里

身份证、手机号、实名信息会被**多个场景**（订酒店、订机票、以后还有别的）使用。若放在场景里：

| 问题 | 后果 |
|---|---|
| 一份信息存 N 份 | 订一次酒店、一次机票就是两份；场景一多就有十几份 |
| 更新要改 N 处 | 换手机号要逐个场景改，漏一个就是错数据 |
| 泄露面 ×N | 任何一处被读走，都是同一份最敏感的信息 |
| 责任不清 | 到底是"场景要的"还是"你给的"分不清 |

**正确做法**：资料放在**独立的一层**，场景里只留**引用 + 使用目的**。

## 二、设计原则（五条）

1. **单独存放**：新增 `profiles` 集合，与场景解耦；场景只写"我要用哪一项"，不存值。
2. **按用途分项授权**：不是"允许场景读我的身份证"，而是——
   「本次订这家酒店，允许把【姓名 + 身份证号】交给**这家酒店**，用途：实名登记，**10 分钟**后失效。」
   一次一授权：限用途、限接收方、限时间。
3. **默认不落明文**：加密容器内部再做**字段级加密**；界面默认只显示掩码
   （`3301**********1234`、`138****8888`），需要看全量时要**再验一次身份**。
4. **调用方与模型永远拿不到**：智能体只能请求"用我的实名信息完成这一步"，
   真正的填充在本机由**执行器**完成，不进入模型上下文。
5. **全程留痕**：哪一次、哪个场景、哪个接收方、用了哪几项、何时失效——可查、可导出。

## 三、落地形态（复用现有机制，不新造概念）

```
① 新集合 profiles（加密存储 + 字段级加密）
   字段：姓名 / 身份证号 / 手机号 / 常用地址 / 邮箱，各带【已验证 | 未验证】
   关联：principal（"本人"）↔ profile

② 授权：authorizations 增加一类 source = "profile:<principal_id>"
   grantee = 场景 / 动作 / 具体接收方
   附带：purpose（用途）、ttl（有效期）、fields（允许用的字段清单）

③ 场景引用：场景的 required_inputs 里声明 { from_profile: "id_card" }
   而不是让调用方每次提交 —— 运行时由本机从 profiles 取，注入本次调用

④ 执行器（本机、不经过模型）：只在"真的要提交给酒店/航司"那一步解密并使用
   智能体拿到的是「完成 / 未完成 + 脱敏回执」，不是明文

⑤ 留痕：每次使用写一条记录（场景、接收方、字段清单、时间、失效时间、结果）
   与现有的判定留痕同一套表，审计口径统一
```

## 四、三个必须接受的权衡

1. **越方便越危险**：一键自动填实名最省事，但一旦被滥用就是最严重的泄露。
   → 所以不做"永久授权给所有场景"，只做**一次一授、短时有效**。
2. **模型不能见**：任何进入模型上下文的内容都可能被留存。
   → 实名信息只能走本机执行器；智能体只看到"完成/未完成"。
3. **与现状有差距**：现在的场景是"调用方提交全部字段"。要支持"字段可来自本机资料库"，
   是一次**真实的架构改动**，不小。

## 五、建议分两步走

**第一步（小，先做）**
- 建 `profiles` 集合（加密 + 字段级加密）
- 控制台能录入、能看到**掩码**，看全量要再验身份
- 与"本人"主体关联
- 此时**不接入任何场景**（先把它安全地存起来）

**第二步（大，后做）**
- 场景声明"这一项来自本机资料"
- 运行时注入 + 一次性短时授权（限用途、限接收方、限时间）
- 本机执行器负责真正的对外提交，模型与智能体只见脱敏结果
- 全部使用写入留痕，可导出给合规

## 六、一句话回答"放在哪里更好"

**放在独立的「个人资料库」里**（加密、掩码展示、字段级加密），**场景只引用不复制**，
**每次使用一次一授、限用途限接收方、短时有效、全程留痕**。

不要放在：场景实例里（重复且脱管）、调用方那侧（每次要你填、还会进模型上下文）、明文文件里（最危险）。

# 追加：与场景切片配合（已定方案）

**已定路线**：现阶段**由智能体执行**订票/订酒店；**本机执行器**作为未来功能。下表两种形态共用同一套声明，将来切换**不需要改场景**。

## 一、先承认一件事（不能假装安全）

若操作由智能体执行，它**必须拿到真值**才能填表提交；而值一旦进入它的上下文，就可能被写进记忆、日志或另一次调用，**我们无法回收**。
→ 所以界面上必须**如实红标**，而不是"加密了所以安全"。

## 二、字段分两类

| 类别 | 例子 | 处理 |
|---|---|---|
| 判定用（普通） | 市盈率、诉讼占比、客户集中度 | 调用方提交，现状不变 |
| 实名用（敏感） | 姓名、身份证号、手机号 | 标记 `category:"sensitive"`，走本机资料库 |

场景的必填字段增加两个键：

```json
{ "name": "身份证号", "type": "text",
  "source": "profile",        // caller（默认）｜ profile（本机资料）
  "profile_key": "身份证号",
  "category": "sensitive" }
```

## 三、取用流程（智能体执行形态）

1. 场景声明某字段 `source=profile` → 对外契约里标 `provided_locally: true`，调用方不必提交。
2. 智能体调用时，**本机**从资料库取出该字段，补齐进本次请求。
3. **补齐的值不回显在报告里**：报告只写「已由本机资料提供 N 项：姓名、身份证号（值不外发）」。
4. 每次补齐写一条留痕（哪份资料 / 哪几项 / 哪个场景 / 时间 / 用途 / 有效期）。
5. 短时效：本次补齐带一个 id 与 `ttl`（例如 10 分钟），超期再取需重新确认。

## 四、给智能体的三条硬约束（写进契约，让它自守）

- 仅用于本次实名登记，**不得**写入记忆、文件或用于其它调用；
- **不得**转述或展示给本次操作以外的人；
- 用完即弃，会话内不缓存。

> 诚实标注：这三条是**约定**，技术上拦不住。真正的拦截只能靠"本机执行器"。

## 五、红标（本文最重要的一条界面要求）

凡 `category=sensitive` 且 `source=profile`（即"会交给智能体的敏感值"），在场景编辑页与契约页显示红标：

> ⚠️ 这一类值会交给执行本次操作的智能体，存在进入其模型上下文的风险，**发出后无法回收**。

## 六、留痕与反查

- 每次补齐/提交都记录；
- 提供一页反查：「我的身份证被哪些场景、在什么时候、用于什么用途」——敏感信息最需要的功能。

## 七、未来：本机执行器（不改场景即可切换）

将来把「本机补齐后交给智能体」换成「由本机直接提交、只回脱敏回执」，**场景定义不用改**：
同一套 `source` / `category` 声明，只把取用通道从"注入请求"换成"本机代用"。
这条接缝是本设计的关键——所以现在就按 `source` 与 `category` 两个标记来声明，而不是写死在调用方那侧。

# 追加二：预定人信息的正确落法（以订酒店 / 订机票为例）

**结论**：预定人信息属于**本机资料**那一节，**不属于**「我要知道的信息（调用方提交）」。取用时逐字段、带三个限定、并把"不得保留"写进 MCP 返回。

## 一、为什么不放进「输入的信息」

「我要知道的信息」的定义是**调用方必须提交**。若把预定人信息塞进去，会出两个具体问题：

1. 契约里它变成**必填** → 智能体为了完成任务可能**自己编一个看起来像的证件号**（模型幻觉，真实风险）；
2. 缺项判定会把它算成"缺" → 你不填就回"信息不足"，而它本来就是本机的事。

**正确落法**：写在「本场景会用到的本机资料」一节，并在契约里明确
`provided_locally`：「本机提供，调用方无需提交，也不会收到其值」。

## 二、取的粒度：逐字段，不给整份资料

```
【本场景会用到的本机资料】
预定人姓名   ｜ 用途：实名登记 ｜ 资料：本人（可改）
预定人证件号 ｜ 用途：实名登记 ｜ 资料：本人（可改）
预定人手机号 ｜ 用途：接收确认 ｜ 资料：本人（可改）
```
只取列出的这几项；同一份资料里的其它字段**一个字都不给**。

## 三、三个限定（比"一次性"三个字更可执行）

| 限定 | 含义 |
|---|---|
| 限用途 | 仅用于本次「预订酒店」的实名登记 |
| 限接收方 | 仅交给这一家酒店 / 这一家航司 |
| 短时效 | 授权 10 分钟有效，过期需重新确认 |
| 留痕 | 本次给了哪几项、给到谁、何时失效，可反查 |

## 四、"不得保留"要写进 MCP 返回（不只写在文档里）

每次返回里附一段给智能体读的约束：

> 本轮提供的实名信息仅限本次使用；**不得**写入记忆、文件或用于其它调用；**不得**转述给本次操作以外的人。

诚实标注：这仍是**约定**，技术上拦不住。真正的拦截只能靠本机执行器（未来）。

## 五、预定人可以不是本人

```
预定人 ｜ 来源：资料库 ｜ 默认：本人 ｜ 可改选：妈妈 / 同事小王 ｜ 用途：实名登记 ｜ 一次性
```
**每次执行时确认用哪一份**（默认沿用上次，可改）。

## 六、与现状的关系

- 声明层已具备：`framework.profile_inputs = [{name, purpose}]`（分节「本场景会用到的本机资料」）；
- 待实现（见 `samples/impl-local-profile-fill.md`）：运行时补齐、返回只计数不回显、缺项判定认它、契约标注、审计记录。
